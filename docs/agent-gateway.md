# Agent Gateway (experimental)

`sailwright-gateway` lets a coding agent run Sailwright through a host-side
policy, either from a devcontainer or directly on a development machine
(Linux, macOS or Windows). The gateway runs on that machine, exposes a fixed set of
Sailwright operations over [MCP](https://modelcontextprotocol.io) (Streamable
HTTP), and asks you on its own terminal before it runs anything outside a
predefined safe set.

The design rationale is recorded in [ADR 0005](./adr/0005-agent-gateway.md). The main use today is automated testing of Sailwright on real hosts; see
[Deterministic E2E scenarios](./testing-workflows.md#deterministic-e2e-scenarios).

> **Status:** experimental. Interfaces, tool names and configuration may change.

## How it works

```text
agent / E2E tests (same machine or devcontainer)
   │  sailwright-gateway connect (stdio MCP bridge)
   │  Unix socket (Linux) or TCP (Docker Desktop) + bearer token
   ▼
sailwright-gateway  (host, your user account, foreground terminal)
   auth · source/Host/Origin checks · safe set or approval · snapshots
   · one job at a time · audit log
   │  argv without a shell, clean environment
   ▼
sailwright (pinned copy)  →  hypervisor  →  VMs
```

- The gateway only knows **how** commands may run. Test scenarios live
  separately in `test/e2e` and use the gateway as a normal client.
- The gateway does not import Sailwright internals. It reads the valid
  targets of the pinned binary at runtime with `sailwright <command> list --json`.
- It follows the extension naming scheme (`sailwright-<name>`), but it is a
  standalone program and does not need the extension interface.

## Security model

The agent, and everything it reads, is treated as untrusted.

- **Only a pinned binary runs.** At startup the gateway copies the Sailwright
  binary you choose into its state directory, shows its SHA-256 and asks you
  to confirm. Only that copy runs jobs and it is re-hashed before every
  run. Agents can't supply, build or swap the binary. To test new code,
  rebuild on the host and restart the gateway. The one exception is a
  startup compatibility probe, `sailwright --gateway-metadata`, of the
  `sailwright` on your PATH, run without `env_passthrough` values. That binary
  is not pinned or confirmed. Its answer only decides whether the gateway warns
  about, or in shared mode refuses, an incompatible CLI. It never runs jobs.
  Anything that can change your PATH can already run code as you.
- **Safe set vs. approval.** Calls are parsed with a strict grammar. Safe
  calls run immediately with a canonical command line generated by the
  gateway. Everything else waits for `approve <id>` on the gateway terminal.
  The agent has no way to answer that prompt; approvals are never accepted
  over the network.
- **Ansible runs on the host**, even for VM targets. Custom playbooks,
  inventories, role sources and arguments after `--` are therefore code
  execution on the host and always need approval. In the safe set only the
  playbooks embedded in the pinned binary can be selected, by name.
- **Snapshots against late edits.** Files from the agent's workspace are
  only used through `bundle_root`. The gateway copies that directory into a
  read-only snapshot before asking you, shows its tree hash, and runs the
  snapshot. Editing the files after approval changes nothing.
- **No shell, clean environment.** Commands are started directly with an
  argument list. The child environment is rebuilt from a short allowlist plus
  `env_passthrough`; `SSH_AUTH_SOCK`, cloud credentials and similar host
  variables are not passed on. stdin is `/dev/null`, which Sailwright treats
  as non-interactive, so prompts are skipped or fail instead of hanging.
- **Shared data, private config.** By default the gateway and CLI share app-data
  and caches. Config and extracted playbooks remain gateway-owned: your
  `ansible-role-sources.yml` is never loaded by gateway jobs. CLI file locks
  reject concurrent operations on the same target. See [Disk usage](#disk-usage).
  Sharing also widens what the safe set reaches: `vm_build` and
  `artifact_pull` replace images in your cache. Your own VMs stay yours: only
  VMs that the gateway created (recorded in `owned_vms.json` in the state
  directory) are open to the agent without asking. For any other VM,
  `vm_start`, `vm_stop`, `vm_destroy` and `vm_provision` become approval jobs,
  tunnels are refused, and `vm_info` shows an access request on the gateway
  terminal. Approving that request opens the VM (credentials, tunnels and
  lifecycle jobs) to the agent until the gateway stops or the VM is
  destroyed. A gateway `create` that fails after deployment began still counts
  as the gateway's, so the agent can destroy what it left behind; a `create`
  refused because your VM already exists claims nothing. Ownership ends when the
  gateway destroys the VM, or when a target listing shows that you destroyed it.
  On libvirt and Hyper-V, records and grants also name the hypervisor instance
  id (`sailwright vm identity`). A VM you destroy and recreate under the same
  name is a new instance, so `vm_info`, tunnels and lifecycle jobs treat it as
  yours even before the next target listing. Lifecycle jobs check the instance
  right before their command runs, not when the agent calls the tool: a Hyper-V
  query can take a minute, so the call returns a running job at once, and the
  job turns into an approval job if the instance changed. UTM and Tart report no instance
  id: there, a VM you destroy and recreate before the gateway next lists
  targets (after any job, and at startup) is still treated as the gateway's,
  so the agent gets its credentials, tunnels and lifecycle jobs without
  asking. On macOS hosts, destroy gateway VMs through the gateway, or restart
  it before recreating one of its target names yourself.
  Use `state_isolation: isolated` for complete separation.
- **Transport.** Agents reach the gateway through a Unix socket in a
  dedicated agent folder (`~/.sailwright-gateway`) that you mount read-only
  into the devcontainer. Access is limited by file permissions (`0600`) and by
  which container gets the mount; nothing is exposed on the network. On
  macOS and Windows (Docker Desktop) the gateway also listens on
  `127.0.0.1:7391`; on Linux that TCP listener is off by default
  (`listen: off`). Wildcard addresses are refused. Every request needs the
  bearer token. TCP requests must also come from an allowed source address
  with an allowed `Host` header, and browser `Origin` headers are rejected.
- **Limits.** One job at a time, a job timeout, a minimum free disk check for
  build/create/pull, output limits, process tree termination on cancel, and
  secret redaction in output and logs.
- **Audit.** Every request, approval decision and job result is appended to
  `audit.jsonl` in the state directory.

> **Caveat:** hypervisor VM names are global. If you also use Sailwright
> yourself on the same host, an agent's `vm_destroy` for `ubuntu/server/amd64`
> affects the same VM name as your own. Use a separate host user or machine
> when that matters.

## Quick start

### Agent on the same machine

On a dedicated development machine or VM, build and start the gateway locally:

```bash
make build-cli-local build-gateway-local
./dist/<os>-<arch>/sailwright-gateway serve --binary ./dist/<os>-<arch>/sailwright
```

Put `sailwright-gateway` on the agent's PATH and register `sailwright-gateway
connect` as the stdio MCP server, using the same `.mcp.json` as a devcontainer.
The connector discovers `~/.sailwright-gateway/gateway.sock` and its token
without a bind mount. On Windows it uses local loopback TCP instead. Run
`sailwright-gateway connect --check` to verify the selected endpoint.

Explicit `SAILWRIGHT_GATEWAY_URL`, `SAILWRIGHT_GATEWAY_DIR` and
`SAILWRIGHT_GATEWAY_TOKEN` settings still take precedence. With a custom agent
directory and TCP transport, set the URL explicitly to the gateway's loopback
listener. The connector never starts a server or chooses a binary to pin.

The same safe set, approval rules and audit apply. Running the agent and gateway
as the same OS user does not create a filesystem sandbox between them. An agent
may build and pin the local binary itself only when the operator has authorized
that workflow in the dedicated development environment.

### Agent in a devcontainer

Use these three steps when the agent runs in a container and the gateway runs
on its host.

1. **On the host:** build from a checkout you trust and start the gateway in a
   terminal you keep open:

   ```bash
   make build-cli-local build-gateway-local
   ./dist/<os>-<arch>/sailwright-gateway serve --binary ./dist/<os>-<arch>/sailwright
   ```

   On macOS or Linux you can install both binaries with Homebrew instead,
   then pass `--binary "$(brew --prefix)/bin/sailwright"`:

   ```bash
   brew install csautter/sailwright/sailwright csautter/sailwright/sailwright-gateway
   ```

   The [install script](./installation.md#install-script) installs both
   binaries on macOS, Linux and Windows as well.

   Alternatively, download `sailwright_<version>_<os>_<arch>` and
   `sailwright-gateway_<version>_<os>_<arch>` from the same
   [release](https://github.com/csautter/sailwright/releases) and verify them
   against the release checksums (see [SECURITY.md](../SECURITY.md)).

   Confirm the SHA-256. The gateway creates `~/.sailwright-gateway/` with only
   `gateway.sock` and a copy of the token. For unattended use pass
   `--binary-sha256 <hash>` instead; approvals still need an interactive
   terminal.

2. **In `devcontainer.json`:** mount that folder read-only and make sure it
   exists before the container starts:

   ```json
   "initializeCommand": "mkdir -p \"${localEnv:HOME}/.sailwright-gateway\"",
   "mounts": [
     "source=${localEnv:HOME}/.sailwright-gateway,target=/run/sailwright-gateway,type=bind,readonly"
   ]
   ```

   The container also needs the `sailwright-gateway` binary for the `connect`
   bridge. This repository needs no edits: `.devcontainer/initialize-host.sh`
   creates the folder and mounts it through a generated compose override (see
   [.devcontainer/README.md](../.devcontainer/README.md)), and
   `postStartCommand` runs `go mod vendor && go install ./cmd/sailwright-gateway`
   on every container start, so the binary always matches the checkout.

3. **For the agent:** register `sailwright-gateway connect` as a stdio MCP
   server. This repository ships it as `.mcp.json`:

   ```json
   {
     "mcpServers": {
       "sailwright-host": { "type": "stdio", "command": "sailwright-gateway", "args": ["connect"] }
     }
   }
   ```

Check the connection inside the container with
`sailwright-gateway connect --check`. It prints where it found the gateway.

`connect` finds the gateway by itself:

1. `SAILWRIGHT_GATEWAY_URL`, if set (`http://host:port/mcp` or `unix:///path/gateway.sock`).
2. The directory selected by `SAILWRIGHT_GATEWAY_DIR`, if set; otherwise the
   mounted `/run/sailwright-gateway` directory when its token exists.
3. The current user's `~/.sailwright-gateway`, when no mounted token is present.

Within the selected directory it prefers a reachable Unix socket. Without one,
container directories use `http://host.docker.internal:7391/mcp`; the default
local user directory uses `http://127.0.0.1:7391/mcp`. A mounted token stays
paired with the container host even when a local gateway also exists. This
preserves Docker Desktop behavior, where the mounted socket is not usable.

The token comes from `SAILWRIGHT_GATEWAY_TOKEN` or the selected directory's
`token` file. The stdio bridge, VM tunnel client and E2E runner all use this
same discovery.

## Host and container setups

| Setup | How the agent connects | Extra configuration |
| --- | --- | --- |
| Agent and gateway on the same Linux/macOS machine | User Unix socket | none |
| Agent and gateway on the same Windows machine | Loopback TCP | none |
| Linux, Docker Engine (rootful or rootless), Podman | Unix socket | none |
| macOS / Windows, Docker Desktop | TCP via `host.docker.internal` (sockets don't cross the Docker Desktop VM) | none; the token still comes from the mounted folder |
| Agent on another machine | not supported yet | |

Notes:

- **Container user.** The socket is `0600` and owned by the user running the
  gateway. With rootless Docker or Podman, root in the container is that user
  on the host. With rootful Docker, root in the container can access it too.
  A non-root container user under rootless Docker maps to a different host
  user and can't open the socket.
- **Gateway restarts** recreate the socket. Running containers keep working
  because the folder, not the socket file, is mounted.
- **Windows hosts** have no agent socket; the gateway uses TCP only.

### Advanced: TCP on Linux

You normally don't need this on Linux, where the TCP listener is off by
default. If you want TCP anyway, set `listen` explicitly; the address must belong to the host, and the container must be able to reach it:

- **Rootful Docker:** bind to the bridge gateway, e.g. `listen: 172.17.0.1:7391`,
  add `allowed_source_cidrs: [172.17.0.0/16]` and `allowed_hosts: [172.17.0.1]`,
  and set `SAILWRIGHT_GATEWAY_URL=http://172.17.0.1:7391/mcp` in the container.
- **Rootless Docker:** `172.17.0.1` only exists inside Docker's own network
  namespace and can't be bound on the host. Use the socket.

Never bind to `0.0.0.0`; the gateway refuses it. Never bind to a hypervisor
network such as libvirt's `virbr0`, where your VMs live.

## Configuration

The gateway reads `gateway.yaml` from its state directory (default:
`<user config dir>/sailwright-gateway`, override with `--state-dir`). All
fields are optional; unknown fields are an error. The state directory must
not be inside an agent workspace or a git checkout.

```yaml
listen: 127.0.0.1:7391            # "off" disables TCP (the Linux default); not allowed on Windows
allowed_hosts: [localhost, 127.0.0.1, "::1", host.docker.internal]
allowed_source_cidrs: [127.0.0.0/8, "::1/128"]
binary: /home/me/sailwright/dist/linux-amd64/sailwright
# binary_sha256: <hex>            # skip the interactive confirmation
data_dir: /home/me/.local/share/sailwright-gateway   # ISOs, images, build caches
agent_dir: /home/me/.sailwright-gateway     # socket + token copy, mounted into containers
state_isolation: shared           # isolated keeps VM state and caches gateway-owned; see Disk usage for the default
# shared_cache_dir: /home/me/.local/share/dev-alchemy/cache   # reuse your CLI cache, see Disk usage
env_passthrough:                   # values are redacted from output and logs
  - LIBVIRT_UBUNTU_ANSIBLE_PASSWORD
pull_allowlist:                    # registry/namespace prefixes for artifact_pull
  - ghcr.io/csautter/sailwright
agent_workspaces:                  # container path -> host path of the bind mount
  - agent: /workspaces/my-roles
    host: /home/me/Projects/my-roles
job_timeout: 6h
approval_ttl: 10m
min_free_disk_gb: 20               # 0 or unset means the default (20); -1 disables the check
clean_prompt_min_gb: 20            # offer to delete the cache on Ctrl+C from this size; 0 or unset means 20; -1 disables
output_limit_bytes: 8388608
snapshot_max_bytes: 52428800
snapshot_max_files: 5000
max_tunnels: 16                   # simultaneous SSH/WinRM streams
tunnel_idle_timeout: 5m
# tunnel_allowed_cidrs: [10.20.0.0/16]   # routed guest networks; host-interface subnets are always allowed
view_listen: 127.0.0.1:0           # build live view, loopback only; port 0 picks one; "off" disables
screen_stuck_after: 15m            # hint when console and output stay unchanged; "off" disables
```

## Tools

| Tool | Tier | Maps to |
| --- | --- | --- |
| `gateway_info` | info | host, binary hash, targets, playbooks, approval state, limits (timeout, output, snapshot, disk) |
| `list_targets` | info | `sailwright <command> list --json` |
| `command_help` | info | `sailwright [command] [list] --help` |
| `vm_info` | info | `sailwright vm info`; guest credentials, SSH config and Ansible inventory |
| `vm_build`, `vm_create`, `vm_start`, `vm_stop`, `vm_destroy` | safe | the matching command for one listed target |
| `vm_provision` | safe | `provision <vm>` with an embedded playbook, `--check`, `--verbosity` |
| `artifact_pull` | safe | `pull <ref> --yes --no-docker-credentials` for allowlisted references |
| `provision_local` | approval | `provision local --yes [--check]` on this host |
| `install` | approval | `install [--with-go] [--virtualbox] [--hyperv] [--vagrant]` |
| `run_cli` | safe or approval | any command line; safe if it parses into the safe set |
| `job_status`, `job_output`, `job_cancel`, `job_list` | control | job handling |
| `job_screenshot` | safe | VM console image of a build job (read-only) |

Operations run as jobs. Poll `job_status` and read `job_output` from
`next_offset`. Only one job runs at a time.

To watch a job on the host, follow the log file the gateway prints when the job
starts (`tail -f <state-dir>/logs/<job>.log`), or start the gateway with
`--follow` to mirror all job output to its terminal. Approval prompts still
appear there.

The safe set never includes `local` or `all` targets, custom paths,
arguments after `--`, `push`, credentials or TLS options, or parallel builds.

## Build console

Builds can print nothing for a long time while the installer runs inside the
VM. During QEMU builds on Linux and macOS hosts the sailwright CLI records the
VM console over VNC (about a minute after the build starts). The gateway
samples the newest frame every 10 seconds and keeps the last 20 frames per
build job.

- `job_status` reports `last_output_at`, `screenshot_available`,
  `screen_changed_at` and `stuck_suspected`. Frames are compared on a coarse
  grid, so a blinking cursor or a spinner is not a change, while new text, a
  progress step or a dialog is. `stuck_suspected` is set when neither the
  console nor the output changed for `screen_stuck_after` (default 15 minutes).
  It is only a hint; the gateway never cancels a job because of it. The
  gateway terminal shows one line when it happens.
- `job_screenshot` returns the console as a JPEG image plus a short JSON
  summary. `index` selects an older kept frame (0 is the newest). Agents
  should call it when the user asks to see the VM, not on every poll.
- The **live view** is a small page for the human on the host. The gateway
  prints its address at startup and when a build starts, for example
  `http://127.0.0.1:41234/view/<token>/`. Open it in a browser on the host;
  it refreshes every 5 seconds and marks a possibly stuck build. It listens on
  loopback only, uses its own random token (not the bearer token, new on every
  start), accepts only `GET`, and is never sent to agents.

Windows hosts (Hyper-V, VirtualBox) do not record the console, so
`job_screenshot` explains that no frame is available.

## Approvals

When a request leaves the safe set, the gateway terminal shows:

```text
================ APPROVAL REQUIRED ================
id:        3f2a9c1d
tool:      run_cli
command:   sailwright provision ubuntu --playbook /home/me/.config/sailwright-gateway/staging/bundle-123/site.yml
workdir:   /home/me/.config/sailwright-gateway/staging/bundle-123
binary:    sha256 157c…
bundle:    /workspaces/my-roles/ansible (host /home/me/Projects/my-roles/ansible)
snapshot:  12 files, 8812 bytes, tree sha256 9b1e…
risk:      HOST-CODE
not safe:  custom playbook paths run Ansible code on the host and need approval
agent note (untrusted): test the new java role against the VM
expires:   14:05:31
Type "approve 3f2a9c1d" or "deny 3f2a9c1d" and press Enter.
===================================================
```

- Review the snapshot directory before approving; it is exactly what runs.
- **sudo for local provisioning (Linux and macOS):** roles with `become: true`
  need your sudo password. For `provision local` requests the prompt also
  offers `approve-sudo <id>`. The gateway then asks for the password on its
  terminal with hidden input, passes it to that one run only through a
  temporary owner-only file (`ansible-playbook --become-password-file`, needs
  ansible-core 2.12 or newer), and deletes the file when the job ends. The
  password is redacted from output, logs and the audit log; the agent only
  sees `"sudo_password": true` on the job. Plain `approve` runs without a
  password, which works if no role needs `become`. Requests that pass
  `--ask-become-pass` (`-K`) are refused, because jobs have no terminal to
  prompt on; use `approve-sudo` instead. When the request sets
  `--inventory-path` or passes Ansible arguments after `--`, the prompt shows a
  `WARNING:` line: both can point the `local` play at another host (for example
  `-i`, `--inventory-file` or `-e ansible_host=...`), which would then receive
  your password. Check the command before using `approve-sudo`. On Windows,
  local provisioning uses a temporary administrator account instead of sudo.
- Building, creating, starting and provisioning VMs never needs sudo on the
  host. On Linux, do the one-time setup yourself in a normal terminal
  (`sailwright install`, membership in the `libvirt` and `kvm` groups, the
  ACL and `virsh net-start` hints the CLI prints), then start the gateway in a
  session where the new group membership is active.
- Each approval is single-use and expires (`approval_ttl`). Only one request
  can be pending.
- Risk flags are hints: `HOST-MODIFYING`, `HOST-CODE`, `PASSTHROUGH-ARGS`,
  `EXTERNAL-PATHS`, `NETWORK-WRITE`, `CREDENTIALS`, `ALL-TARGETS`.
- Other console commands: `approve-sudo <id>`, `pending`.
- Without an interactive terminal (or with `--no-approvals`) the approval
  tools are disabled and only the safe set is available.
- `serve --bypass-approvals` is for disposable test hosts only. It approves
  every request and every access request for VMs the gateway did not create,
  pins the binary without asking, and works without a terminal. Any agent
  with the token can then run everything the gateway grammar accepts. The
  console prints each automatic decision, and `audit.jsonl` marks it with
  `"auto_approved": true`. It cannot be combined with `--no-approvals`.

## Disk usage

When `state_isolation` is unset, new gateways use `shared`. If `data_dir/app`
from an older gateway exists, the gateway keeps `isolated` so that those VMs
stay managed, and prints a startup note; set `state_isolation: shared`
explicitly after destroying them.

In `shared` mode, gateway jobs use the normal CLI's
app-data and cache directories, including `DEV_ALCHEMY_APP_DATA_DIR`,
`DEV_ALCHEMY_CACHE_DIR`, `DEV_ALCHEMY_VAGRANT_DIR` and
`DEV_ALCHEMY_PACKER_CACHE_DIR` overrides. Images and created VM state are
shared, so builds do not need a second copy of the same image.

Config always stays at `data_dir/config`. Embedded assets from the pinned
binary are extracted under `data_dir/embedded/project`, independently of the
shared data (the gateway passes `SAILWRIGHT_EMBEDDED_DATA_DIR` to its jobs;
this variable is internal to the gateway). `DEV_ALCHEMY_CONFIG_DIR` and project overrides from the host do
not redirect gateway jobs to your normal role-source configuration.

Set `state_isolation: isolated` to keep app-data under `data_dir/app`, as in
older versions. `shared_cache_dir` remains a deprecated explicit cache override
in either mode, and the gateway prints a deprecation warning when it is set. It
never changes the config location.

CLI operations acquire operating-system file locks under app-data `locks/`.
The same target cannot be built, created, started, stopped, destroyed or
provisioned concurrently. Different targets may run concurrently; `all` and
registry transfers acquire an exclusive lock covering all targets. A competing
command exits with a `resource busy` error, immediately by default or after
waiting up to `SAILWRIGHT_LOCK_TIMEOUT` (a Go duration such as `30s`), that
names the holder, for example `held by pid 4242 (sailwright create
ubuntu/server/amd64) since 14:03:12`. Gateway jobs wait up to 30 seconds.
Locks are released on process exit; lock files remain in place and should not
be removed.

Lock protocol 2 moves the Windows lock byte away from holder metadata. Update
both the pinned and installed CLI together; protocol 1 binaries cannot safely
share state with protocol 2 binaries on Windows.

At startup the gateway checks the pinned CLI's state schema and locking
protocol, and compares them with `sailwright` on PATH when installed (skipped
when that is the pinned file). Shared mode refuses a pinned CLI with an
incompatible or missing contract, and an installed CLI that reports an
incompatible one. An installed CLI from before locking support only produces a
warning: it cannot take locks, so do not run it while gateway jobs use the
shared state, and update both binaries together. Compatible version differences
produce a warning.

Existing `data_dir/app` is left untouched. With `state_isolation: shared` set
explicitly, a one-time startup notice explains how to select isolated mode or
remove the old data (including its extracted `project/` directory) after
destroying its VMs.

**Cleaning:** shared mode never deletes the user's cache, even with `--yes`.
In isolated mode, `sailwright-gateway clean` empties only gateway-owned cache
and Packer-cache directories while the gateway is stopped. VM disks, Vagrant
state, config and an explicit shared cache are preserved. The shutdown cache
question follows the same ownership rules.

## Files in the state directory

| Path | Content |
| --- | --- |
| `token` | bearer token (owner-only permissions) |
| `gateway.yaml` | optional configuration |
| `bin/sailwright` | pinned binary copy |
| `data/` | gateway-owned config and extracted assets; only with `--state-dir` or on macOS: the data dir, see [Disk usage](#disk-usage) |
| `work/` | empty working directory for commands |
| `staging/` | read-only bundle snapshots, removed after each job |
| `logs/<job>.log` | redacted output per job, capped at 64 MiB; removed with the job history and after 30 days |
| `screens/<job>/` | last sampled build console frames, cleared on restart |
| `audit.jsonl` | audit log, including `gateway_started` / `gateway_stopped` with version and binary hash |

The agent folder (`agent_dir`, default `~/.sailwright-gateway`) is separate
from the state directory and only holds `gateway.sock` and a copy of `token`.
It must not overlap the state or data directory or an agent workspace.

## VM access

`sailwright vm info ubuntu --type server --arch amd64 --json` reports a
running VM's engine, address, network mode, protocol, port and guest
credentials in schema version 1. Text output is available without `--json`; it
masks the password unless you pass `--show-password`. Address discovery is
deliberately separate from `list --json`, where `address` remains null. The
command never starts a stopped VM.

Network modes are `nat` (reachable only from this host), `bridged` (on your
LAN), `user` (libvirt user-mode networking on `qemu:///session`) or `unknown`:

| Engine | Mode |
| --- | --- |
| libvirt | from active domain/network XML: `nat` for NAT forwarding, `user` for user interfaces, `bridged` for bridge/direct interfaces; `unknown` on query failure, routed networks or mixed modes |
| Tart | `unknown`; the querying shell cannot establish how the running VM was started |
| Hyper-V | from the type of the switch the VM is attached to: `Internal` is `nat`, `External` is `bridged` |
| UTM | `unknown` |

The libvirt URI and the name `default` do not prove NAT isolation. Tart's
`TART_MACOS_BRIDGED_INTERFACE` affects guest startup, but is not used to infer
an existing guest's network mode. Unknown modes retain the LAN audit warning.

On Hyper-V the guest reports its addresses through integration services, so
the host decides which one to use. `vm info` and provisioning take an IPv4
address of an adapter on a host-reachable switch (`Private` switches are
skipped), preferring the switch in `VAGRANT_HYPERV_SWITCH` (default
`Default Switch`). When the host has an address on that switch's
`vEthernet (<switch>)` adapter, the VM address must be in the same subnet.
This works for the Windows Default Switch (a random `172.x` subnet), for the CI
runners' internal switch with NAT (`192.168.0.0/24`) and for external switches.
Addresses of containers or other interfaces inside the guest are ignored. If
the Hyper-V query fails, takes longer than 10 seconds or reports no usable
address yet, Vagrant discovery is tried and its answer must pass the same
checks. `sailwright provision` on Hyper-V uses the same discovery. Gateway jobs do not receive
`VAGRANT_HYPERV_SWITCH` or `TART_MACOS_BRIDGED_INTERFACE`; add them to
`env_passthrough` if the agent's VMs should use the same network as yours.

Call MCP `vm_info` with the same target to receive guest credentials, an
`ssh_config` block and an Ansible inventory. These contain sensitive guest
credentials; keep inventory files private. The gateway does not write them to
audit or job logs. Its config remains separate from your CLI config.

Save `ssh_config` to a container file, then use its `Host` alias. The block
shares one connection between ssh and scp calls (`ControlMaster auto`,
`ControlPersist 60s`) with a socket in `~/.ssh`, which must exist
(`mkdir -m 700 -p ~/.ssh`). A shared connection stays usable for up to 60
seconds after its last session, also after the VM's access was revoked; add
`ControlPath none` before the generated block to turn sharing off. Ansible's SSH
connection already shares connections this way.

```bash
ssh -F ./ssh_config sailwright-ubuntu-server-amd64
scp -F ./ssh_config ./artifact sailwright-ubuntu-server-amd64:/tmp/artifact
```

SSH asks for the returned guest password. Agents usually cannot answer a
prompt, so pass it non-interactively, for example with `sshpass` (the password
stays out of the process list with `-e`):

```bash
export SSHPASS='<password from vm_info>'
sshpass -e ssh -F ./ssh_config -o UserKnownHostsFile=./known_hosts \
  -o StrictHostKeyChecking=accept-new sailwright-ubuntu-server-amd64 true
```

Without `sshpass`, point `SSH_ASKPASS` at a script that prints the password
and set `SSH_ASKPASS_REQUIRE=force`. Ansible uses `ansible_password` from the
generated inventory and needs `sshpass` installed for SSH hosts.

SSH host keys are checked normally. For disposable VMs, use a dedicated
`UserKnownHostsFile` with `StrictHostKeyChecking=accept-new` as above, and
remove the old entry when recreating a guest; avoid changing your normal host
keys.

The generated ProxyCommand is:

```bash
sailwright-gateway vm tunnel ubuntu/server/amd64 22
```

It writes only guest bytes to stdout, and discovers the gateway and token in
the same way as `connect`. Targets always have three slash-separated fields;
Windows and macOS have an empty type, for example `windows11//amd64`.

For SSH Ansible, save `ansible_inventory` as an owner-only JSON file (JSON is
also valid YAML) and run your playbook from the container:

```bash
chmod 600 inventory.json
ansible-playbook -i inventory.json site.yml
```

Install the usual SSH password-auth dependency (`sshpass`) in the controller
container when using password authentication. Your roles now execute on the
container's Ansible controller, with the guest as the target.

WinRM needs a local listener because its Ansible connection has no
ProxyCommand. Run the `listen_command` returned by `vm_info` in a separate
container terminal, for example:

```bash
sailwright-gateway vm tunnel windows11//amd64 5985 --listen 127.0.0.1:15985
```

Keep it running while Ansible uses the returned inventory. The inventory maps
WinRM to that local port. Port 5986 uses 15986. Install `pywinrm` in the
controller container. The listener accepts explicit loopback addresses only.

**Tunnel policy:** `/tunnel` uses authenticated HTTP/1 upgrade behind the same
source, Host, Origin and bearer checks as MCP. Only ports 22, 5985 and 5986 are
allowed, and only the ones that match the VM's protocol: 22 for SSH guests,
5985 and 5986 for WinRM guests. The destination address comes exclusively
from the pinned CLI, refreshed for every new tunnel. Some engines learn that
address from the guest itself (libvirt guest agent, Hyper-V integration
services), so a guest the agent controls can report a different address. The
gateway therefore only connects to addresses inside a subnet of one of the
host's own network interfaces: the hypervisor's NAT bridge or switch, or your
LAN for bridged guests. Routed destinations, such as the internet, other VLANs
or networks behind a VPN route, are refused. If your guests sit on a routed
network that no host interface covers, add it to `tunnel_allowed_cidrs`. The
remaining risk is accepted: a guest on a bridged network can still point the
tunnel at another LAN host on the guest's port. The gateway protects the host
OS from the agent, not your network, and an agent in a devcontainer usually
reaches the LAN directly anyway. If you restrict the container's network, keep
in mind that tunnels to bridged guests are a path around that restriction.
Loopback, link-local, multicast, unspecified and host-owned addresses are
rejected, including mapped IPv4 addresses. Bridged/LAN guests are allowed;
`bridged` or `unknown` network modes produce a `LAN_OR_UNKNOWN_NETWORK` audit
warning. There are at most `max_tunnels` connections; inactive streams close
after `tunnel_idle_timeout`. Shutdown closes active streams. Audit events
record denied requests, opening, closing, target, port, duration and byte
counts; they never contain guest passwords.

Guest passwords returned by `vm info` are redacted from job output and logs
for the rest of the gateway run. A password equal to the guest username, such
as `vagrant`/`vagrant`, is not hidden. It is not secret, and hiding it would
replace that word everywhere, including in paths like `/home/vagrant`.

VM information has a two-second cache for repeated MCP calls. Tunnel creation
bypasses it, so a recently stopped guest cannot be reached using cached info.
Concurrent lookups for the same target share one CLI call; different targets
are looked up in parallel. A refused tunnel prints the gateway's reason, for
example `tunnel refused: HTTP 404: managed VM is unavailable or not running`.
When a lookup fails, the gateway terminal shows the CLI's reason (redacted),
for example `vm info ubuntu/server/amd64 failed: ... exited with 1: VM is not
running`, and `vm_info` returns the same reason to the agent.
The tunnel transports SSH or WinRM; it never runs a host shell.

### Testing disposable guest access

Build the Ubuntu image on the host first, then use a target that does not
already have a VM. With the gateway running and `ssh`, `scp`, `sshpass` and
`sailwright-gateway` installed in the container:

```bash
SAILWRIGHT_VM_ACCESS_E2E=1 SAILWRIGHT_E2E_TARGET=ubuntu/server/amd64 \
  go test -tags e2e ./test/e2e -run '^TestVMAccess$' -count=1 -timeout 1h -v
```

This preflights existing state, creates and starts the VM, obtains `vm_info`,
runs `uname -a` through SSH, copies a file with scp, verifies it in the guest,
and destroys the VM even after failure. It needs a real host gateway and is
skipped unless explicitly enabled. The ordinary gateway suite uses a fake CLI
and TCP guest to test policy and stream handling without a hypervisor.

On a Windows gateway host the test also runs natively, without a devcontainer
or WSL: it uses the Windows OpenSSH client, passes the guest password through
`SSH_ASKPASS` (Windows has no `sshpass`) and turns off connection sharing,
which Windows OpenSSH does not support. See
[Testing on a Windows Hyper-V host](#testing-on-a-windows-hyper-v-host).

## Limitations

- GUI access (RDP/VNC) is not exposed by the tunnel.
- One host per gateway; remote hosts over the network are not supported yet.
- On Windows, cancellation terminates the process tree immediately; there is
  no graceful stop signal.

### Guests inside a development VM

Treat the development VM as the gateway host. Probe nested KVM support before
building a guest: CPU virtualization flags and the presence of `/dev/kvm` alone
do not prove that QEMU can initialize it. The Ubuntu QEMU build script already
probes KVM and falls back to software emulation when unavailable;
`DEV_ALCHEMY_QEMU_FORCE_SOFTWARE_EMULATION=1` forces that slower build path.
To pass this override to gateway jobs, explicitly list it in `env_passthrough`.
This build override does not change libvirt's guest runtime configuration.

The development VM still needs normal Linux host prerequisites: QEMU, libvirt,
`virt-install`, access to `/dev/kvm` and the selected libvirt connection. With
`qemu:///system`, enable the libvirt `default` NAT network. Ansible and
`sshpass` are also needed for the provisioning and SSH E2E scenarios. See
[Linux VM testing](./testing-workflows.md) for setup and session-connection
options. A successful gateway smoke test establishes transport and CLI access;
a guest lifecycle test establishes nested virtualization and networking.

Existing desktop sessions retain their old groups after `usermod`. Start the
gateway from a new login session that includes `libvirt`, or run its serve
command through `sg libvirt -c '...'`. You can check the new group access with
`sg libvirt -c 'virsh --connect qemu:///system list --all'` before restarting
the gateway. Follow the CLI's image-directory ACL hints if QEMU cannot access
its managed disks; the controller's access to the libvirt socket and the QEMU
service user's access to disk files are separate permissions.

If a large OCI download fails with an HTTP/2 `PROTOCOL_ERROR`, retrying over
HTTP/1 can help diagnose the network path. Start the local gateway with
`GODEBUG=http2client=0` in its environment and add `GODEBUG` to its existing
`env_passthrough` list so the pinned CLI receives it too. Restart the gateway
after changing those settings. This is an optional registry-transfer workaround;
it does not change guest networking or virtualization acceleration.

### Testing on a Windows Hyper-V host

Run gateway, CLI and client natively on Windows; a devcontainer or WSL is not
needed to exercise the gateway, and WSL is one more Hyper-V guest competing for
CPU and memory. On a disposable test host, approvals can be automated:

```powershell
go build -o .\dist\windows-amd64\sailwright.exe ./cmd/main.go
go build -o .\dist\windows-amd64\sailwright-gateway.exe ./cmd/sailwright-gateway
.\dist\windows-amd64\sailwright-gateway.exe serve `
  --binary (Resolve-Path .\dist\windows-amd64\sailwright.exe) --bypass-approvals
```

In a second PowerShell, with `dist\windows-amd64` on `PATH` for the
`sailwright-gateway vm tunnel` ProxyCommand:

```powershell
$env:Path = "$PWD\dist\windows-amd64;$env:Path"
$env:SAILWRIGHT_GATEWAY_URL = 'http://127.0.0.1:7391/mcp'
$env:SAILWRIGHT_GATEWAY_DIR = "$env:USERPROFILE\.sailwright-gateway"
$env:SAILWRIGHT_VM_ACCESS_E2E = '1'
$env:SAILWRIGHT_E2E_TARGET = 'ubuntu/server/amd64'
Set-Location test\e2e
go test -tags e2e . -run '^TestVMAccess$' -count=1 -timeout 55m -v
```

The audit log (`%APPDATA%\sailwright-gateway\audit.jsonl`) then shows
`vm_info`, paired `tunnel_opened`/`tunnel_closed` events with bytes in both
directions, and `"auto_approved": true` on every decision `--bypass-approvals`
made. `owned_vms.json` next to it holds the VM's Hyper-V id
(`(Get-VM).Id.Guid`) while the VM exists.

When Windows itself runs in a VM (nested virtualization):

- Hyper-V cannot pass virtualization extensions on to its guests. `sailwright
  create` and `start` detect Hyper-V's refusal (Worker-Admin event 3108),
  turn the extensions off for that VM and retry once; set
  `VAGRANT_HYPERV_NESTED_VIRTUALIZATION=false` to skip the first attempt.
- Give the outer VM enough memory for Windows, the 8 GB guest and the tools,
  about 24 GB, and a CPU topology that matches the physical CPU (for example
  `host-passthrough` with 4 cores × 2 threads on an 8-core/16-thread CPU).
  With more virtual cores than physical cores, guests with 4 vCPUs slowed
  down so far that they never reported an IP within Vagrant's 600 s.
- Packer installs of Ubuntu take about 1.5 hours.

To debug a guest that does not come up, read the Hyper-V events first:
`Get-WinEvent -LogName Microsoft-Windows-Hyper-V-Worker-Admin` shows guest
resets (18514), guest kernel crashes with the panic text (18590) and refused
starts (3108). A screenshot of the console comes from
`Msvm_VirtualSystemManagementService.GetVirtualSystemThumbnailImage`. For the
kernel log, connect COM1 to a named pipe (`Set-VMComPort -Number 1 -Path
\\.\pipe\name`) and add `console=ttyS0,115200` to the guest's kernel command
line; the serial console itself slows a nested guest down considerably.
